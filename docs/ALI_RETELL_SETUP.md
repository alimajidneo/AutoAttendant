# Ali's Retell setup checklist

This checklist does not authorize deployment, telephone provisioning, billing, real calls or real calendar writes. Keep billing and auto-recharge off. Saving DeskRoute settings does not purchase a number or place calls.

1. Ali personally signs in, completes MFA and accepts account and voice terms. Provide the intended Retell account and agent identity, and separately authorize technical setup.
2. Configure the webhook-badged API key as server-only `RETELL_API_KEY` through the secret manager. Never paste it into chat, VITE/browser variables or repository files.
3. Only after Ali provides the account/agent and authorizes technical setup may the coding agent configure these two non-secret, server-only allowlist variables:
   - `RETELL_WORKSPACE_ID`: UUID of the approved DeskRoute workspace.
   - `RETELL_AGENT_ID`: exact approved Retell agent identifier.
4. The workspace owner may save an agent ID disabled. **Pending operator approval** means it cannot be enabled until the API key and both server allowlist values match. Managers cannot self-verify ownership; non-owner managers receive owner-only guidance. Changing the environment immediately invalidates stale enabled database mappings on subsequent resolve/ingest requests. No Retell API ownership call is made.
5. Configure the approved origin plus `/api/retell/webhook` for only `call_started`, `call_ended`, `call_analyzed`, `transfer_started`, `transfer_bridged`, `transfer_cancelled`, and `transfer_ended`. Transfer events require the documented top-level `start_timestamp` identifying the attempt; the call's start time is not a substitute. Do not subscribe to transcript streams.
6. Configure **five** signed POST custom functions. Every envelope includes `call: { agent_id, call_id }` and `args`; both call identifiers are required. Signature verification uses the original request body.

   | Function | POST path | Strict args |
   | --- | --- | --- |
   | lookup-employee | `/api/retell/functions/lookup-employee` | Optional `name`, `department` (1–80 characters) |
   | check-availability | `/api/retell/functions/check-availability` | `employeeId`, `start`, `end` |
   | resolve-transfer | `/api/retell/functions/resolve-transfer` | `employeeId` |
   | book-appointment | `/api/retell/functions/book-appointment` | `employeeId`, `start`, `end`, `callerName` (1–100); optional E.164 `callerPhone`, `caller_email`, `caller_phone`, `caller_confirmed` boolean, `purpose` (1–300). Cal requires valid email or phone and explicit confirmation |
   | save-message | `/api/retell/functions/save-message` | `message` (1–1000); optional `callerName` (up to 100), E.164 `callerPhone` |

   Intervals use ISO timestamps with timezone offsets and must last from 5 minutes through 8 hours. Set **`max_retry=0` for book-appointment and save-message**, especially booking. With additive migration 0013, DeskRoute durably stores completed write results. Completed replays return the original result; unresolved/crashed bookings return `status: unknown, reason: reconciliation_required` and must not be retried. Message claim/mutation/result are transactional. See CALCOM_INTEGRATION.md for exact invocation identity and crash recovery semantics. A saved message returns only `saved` and `messageId`. Successful direct booking is confirmed only after provider success and local finalization.
7. Configure `call_analysis.custom_analysis_data.deskroute_outcome` to exactly one of `answered`, `booked`, `escalated`, `abandoned`, `error`. Unknown/malformed analysis does not invent an outcome. Bridging supplies answered; confirmed direct booking supplies booked best-effort; saved messages supply escalated. The dashboard displays Unknown when no outcome is known.
8. Direct transfer resolution rechecks availability for the next five minutes before decrypting. For Cal.com authority, DeskRoute first checks routing, manual availability and full local hours; **Retell must run its Cal.com availability check immediately before resolving the transfer**. Unknown/busy/outside-hours decisions cannot expose the destination. Resolution does not place or bridge a call. Retell pilot configuration must screen the employee and require explicit employee acceptance before joining the caller. Use save-message as the fallback when a person cannot be reached.
9. Each calendar owner personally consents to Google/Microsoft OAuth. The workspace owner initiates the authorized connection flow; a manager configures and assigns approved connections to employees. Only the workspace owner can load personal provider calendar metadata. Employee dashboard accounts and employee self-service OAuth are deliberately deferred; assignment is not proof of employee consent. Employees start with weekday 09:00–17:00 hours; managers can edit weekly intervals while exceptions remain intact.
10. For an ambiguous requested booking, the manager checks the **selected provider calendar** personally. Cancel/release in Appointments only after establishing that no event exists. A timeout, server error, throttling/conflict response, missing event ID or failed local finalization may hide a successful provider write. Only clear client rejections (invalid/auth/not-found-style responses) release the reservation immediately. No worker, retry or automatic reconciliation subsystem exists.
11. Review Retell privacy/retention, recording/AI disclosures and access controls. DeskRoute stores normalized call facts and masked caller numbers, not raw transcripts/recordings or transfer destinations. Message intake is stored in the existing escalation with the caller's disclosed contact details and no transcript excerpt.
12. Approve any future pilot, participants, voice, destination, provider-write scope and spending limit separately. Local tests prove no real call, provider acceptance, employee acceptance or hosted deployment.

Ordinary pilots should use **at most five accounts** per employee. Each function inspection permits at most ten distinct assigned connections and fifty selected references, with at most twenty provider read operations (one calendar-list and one free/busy operation per connection). Adapters may paginate or fan out HTTP requests; this is not a claim of twenty HTTP requests or a measured hosted cost. No polling or cron is added.

Cal.com API-key connections and live-slot booking support are now implemented in source. See [Cal.com setup and reconciliation](CALCOM_INTEGRATION.md). Legacy links remain link-only. Keep `max_retry=0`; only `confirmed` permits a confirmation announcement. No live account was accessed or configured.
